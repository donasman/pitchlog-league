# PitchLog 에이전트 파이프라인

`docs/AGENT_WORKFLOW.md` 1장을 **실행 순서**로 푼 것이다. main(너)이 이 절차를 따른다.
목적은 속도가 아니라 틀린 코드가 조용히 들어오는 것을 막는 것이다.

## 원칙 — 어디까지 되돌릴 수 있나

```
01 탐색 A·B   02 결정   03 설계   04 확정·멈춤 │ 05 구현 A·B   06 검증
 병렬          직렬      직렬      사람 확인    │  병렬          별도
 ←── 뒤집혀도 한 턴. 계약이 아직 움직인다 ──→ │ ←── 계약 동결. 취소하고 다시 띄우는 것뿐 ──→
```

- 병렬은 **01 과 05 에서만.** 02·03 은 절대 병렬로 돌리지 않는다.
- **04 에서 반드시 멈춘다.** 결정 목록을 사용자에게 보여주고 확인을 받기 전에 05 로 가지 않는다.
- 05 부터 **계약 동결.** 이 구간에서는 문서(`docs/`)를 고치지 않는다. 문서 갱신은 06 이 끝난 뒤 `pitchlog-docs-sync`.
- 05 의 지시문에는 확정된 계약을 **문서 참조가 아니라 값으로** 박는다 — 엔드포인트 경로, DTO 필드명·타입, 정규화 후 shape. 절 번호는 근거 인용용으로만 남긴다.
- 05 도중 계약이 바뀌면 진행 중인 구현을 **버린다.** 절반 맞는 결과를 살리지 않는다.

## 00. 시작 전

- 브랜치가 `feature/` · `fix/` · `chore/` 인지 확인한다. `dev` · `main` 이면 먼저 브랜치를 판다 (훅이 커밋을 막는다).
- 이번 작업이 백엔드/프론트 둘로 갈리는지 본다. 한쪽만이면 그쪽 셋만 쓴다. 스택 구분이 없으면(`ingest` · CI · 문서) 범용 `explorer` · `implementer` · `verifier` 를 쓴다.

## 01. 탐색 — 병렬

`backend-explorer` 와 `frontend-explorer` 를 **한 메시지에서 동시에** 띄운다. 각각에:

```
목표        <이번 작업> 에 필요한 기존 패턴을 계약표로 돌려준다
읽을 것     <해당 스택 가이드 절 번호> · <관련 파일 경로>
건드릴 파일  없음 — 읽기 전용
금지        수정 · 상대 스택 보기 · 추측으로 채우기
완료 조건   모든 항목에 파일:줄 · 확인 못 한 것은 "확인 못 함"
보고 형식   계약표 · 어긋나는 것 · 죽은 코드 · 확인 못 한 것
```

## 02. 결정 — main

두 계약표를 읽고 **main 이 정한다.** 탐색이 드러낸 사실에 근거해서만. 예: "displayState 는 프론트 normalize 가 만든다 — getDisplayState 가 죽은 함수라서(탐색 B §3)".

## 03. 설계 — 단일

`planner` 하나. 02 의 결정 목록을 전제로 준다. 산출물에 구현 A/B 가 그대로 쓸 계약이 **값으로** 들어 있어야 한다.

## 04. 확정 — 멈춤

사용자에게 보여준다:

1. 02 의 결정 목록 (각각 근거 파일:줄)
2. 03 의 설계안 요약과 미결정·대안
3. 구현 A / B 파일 집합 — 겹치는 파일이 있으면 어느 쪽에 몰았는지

**여기서 멈추고 확인을 기다린다.** 확인 뒤부터 계약 동결.

## 05. 구현 — 병렬

`backend-implementer` 와 `frontend-implementer` 를 **한 메시지에서 동시에** 띄운다. 여섯 칸을 전부 채운다. 빈 칸이 있으면 보내지 않는다.

```
목표        한 문장
읽을 것     확정 계약 (값으로) · 가이드 절 번호 · 스킬 이름
건드릴 파일  명시적 목록. 이 밖은 수정 금지 — 필요하면 보고하고 멈춘다
금지        이 작업에서 특히 걸리는 것 (스택 고정 원칙은 직무기술서에 있으니 작업 고유의 것만)
완료 조건   백엔드: npx tsc --noEmit -p tsconfig.json 0 오류 / 프론트: npm run verify 통과
보고 형식   바꾼 파일 · 근거(파일:줄) · 실행한 명령과 출력 그대로 · 못 한 것과 이유
```

한 에이전트의 작업량은 **파일 3~5개, 커밋 하나 분량**으로 자른다. 크면 쪼개서 순차로.

**계약을 값으로 박는다는 것 — 예시.** 백엔드 판 지시문에 "DTO 는 backend/src/match/dto/... 를 따른다"
라고 절 번호만 적지 않는다. 필드명·타입·null 여부·API 경로를 **직접** 적는다.

**mock.js 는 계약 원본이 아니다.** 백엔드 판 지시문에서 "frontend/src/services/mock.js 와 shape 맞춤"
같은 요구는 넣지 않는다. 계약은 백엔드 DTO + `normalize.js` 반례 테스트에서 나온다.
프론트 판 지시문에서도 "live PR 이니 mock.js 도 같이 고쳐라" 는 의무로 요구하지 않는다 —
깨지면 그때 별도 판으로 고친다. mocks/lineups.js 9,438줄 같은 대형 Mock 이 실 계약을 밀어내는
것을 막기 위함이다.

## 06. 검증 — 별도

`backend-verifier` 와 `frontend-verifier` 에 각 스택의 `git diff` + 확정 계약을 넘긴다. **문제만** 받는다.
"막아야 함" 이 있으면 해당 implementer 에 되돌린다. verifier 가 고치지 않는다.

**프론트가 바뀐 판은 브라우저 실측을 07 전에 넣는다.** verifier 는 diff · verify · build 만 본다 —
콘솔 경고 · 렌더 결과 · 실 API 왕복은 못 본다. 11장(홈)과 09-08 선수·통계, 두 판 연속 브라우저가
잡았고 둘 다 백엔드·verifier 는 깨끗했다. `VITE_USE_MOCK=false` 로 화면을 실제로 열어 콘솔
경고 0 과 각 렌더 자리를 사용자가 확인한다. 남은 것 있으면 다시 05.

## 07. 마무리

1. `docs/AGENT_RUNS.md` 에 이번 판을 한 줄 적는다 — 넷 중 무엇이 깨졌나
2. `pitchlog-pr-flow` 로 커밋 · push · PR (대상 `dev`). **AGENT_RUNS 도 이 커밋에 함께 태운다**
3. 문서 갱신이 필요하면 **이제** `pitchlog-docs-sync`

AGENT_RUNS 를 커밋 뒤에 쓰면 dev 로 넘어가 있을 확률이 높고 `guard-git` 훅이 막는다
(2026-09-08 첫 판에서 실제로 걸렸다). 브랜치 안에서 쓴다.
