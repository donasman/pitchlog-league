# 발표 대본 — 프론트엔드 (초안 발표용)

> 구성: **핵심 6분** + 선택 블록 2개(각 1~1분 30초).
> 백엔드 대본 뒤에 이어붙이면 전체 **13분 30초**입니다.
> 대괄호 `[ ]`는 말하지 않는 지시입니다.

---

## 0. 넘어가는 말 · 15초

[백엔드에 이어서 하는 경우. 단독 발표면 이 단락 대신 아래 괄호를 쓰세요]

여기까지가 백엔드 설계였고, 이제 화면 쪽을 말씀드리겠습니다.

[단독 발표일 때 — "PitchLog는 유럽 5대 리그와 챔피언스리그의 경기·순위·선수 기록을
보여주는 서비스입니다. 오늘은 그중 화면 쪽을 발표하겠습니다."]

## 1. 순서를 뒤집었습니다 · 50초

[여기서 청중이 "어? 왜?" 하게 만드는 게 목적입니다]

먼저 한 가지 말씀드릴 게 있습니다.
**이 프로젝트는 프론트엔드를 백엔드보다 먼저 만들었습니다.**

보통은 반대죠. 서버를 만들고 화면을 붙입니다.
저는 화면을 먼저 만들었습니다. 이유는 두 가지입니다.

첫째, **화면을 그려봐야 백엔드가 뭘 줘야 하는지 알 수 있습니다.**
순위표를 실제로 만들어보니 "이 팀이 UCL에 나가는지"를 화면에서 계산하면 안 된다는 게 보였고,
그건 백엔드가 줘야 하는 정보라는 결론이 나왔습니다.

둘째, 보여줄 게 빨리 생깁니다. 지금처럼요.

[한 박자]

그런데 여기서 문제가 생깁니다.
**백엔드가 없으면 데이터가 없습니다.**

## 2. 가짜 데이터를 검사한다 · 1분 40초

[이 발표의 하이라이트입니다. 천천히]

그래서 데이터를 제가 손으로 만들었습니다. 여섯 개 대회의 경기, 순위, 선수 기록을 전부요.

그런데 손으로 만들면 **반드시 틀립니다.**
승점을 잘못 더하고, 순위 순서가 뒤집히고, 끝난 경기에 점수를 안 넣습니다.

그리고 이게 무서운 이유는, **화면에는 멀쩡하게 나온다**는 겁니다.
순위표는 잘 그려집니다. 숫자가 틀렸을 뿐이죠.

[한 박자]

그래서 **가짜 데이터를 검사하는 스크립트**를 따로 만들었습니다.
검사가 아홉 개입니다. 몇 개만 말씀드리면,

승점이 승·무·패 기록과 맞는지.
순위가 승점 순으로 정렬돼 있는지.
종료된 경기에 점수가 들어있는지.
챔피언스리그 1차전과 2차전 합산 점수가 맞는지.

[강조]

실제로 이 검사를 만들고 나서 **두 개를 잡았습니다.**
득점 순위 정렬이 틀려 있었고,
챔피언스리그 합산 점수에서 홈팀과 원정팀이 반대로 들어가 있었습니다.
둘 다 눈으로 봐서는 못 찾았을 겁니다.

여기에 다국어 검사 여덟 개를 더해서, 지금 **자동 검사가 열일곱 개** 돌아갑니다.

[중요한 마무리]

그리고 이 스크립트는 **백엔드가 붙어도 안 버립니다.**
진짜 데이터가 들어와도 "승점 계산이 맞는가"는 똑같이 검사해야 하니까요.
가짜 데이터는 버려지지만 검사는 남습니다.

## 3. 형식이 다른 대회를 한 화면에 · 1분 20초

[순위표 그림 띄우고]

다음은 화면 설계에서 가장 고민한 부분입니다.

프리미어리그는 단순합니다. 20팀이 서로 두 번씩 붙고, 위에서 네 팀이 챔피언스리그에 나가고
아래 세 팀이 강등됩니다.

**챔피언스리그는 구조가 아예 다릅니다.**
조별리그가 없어졌습니다. 36개 팀이 **하나의 순위표**에 다 들어갑니다.
그리고 1위부터 8위는 16강 직행, 9위부터 24위는 플레이오프, 나머지는 탈락입니다.

[한 박자]

여기서 선택지가 두 개였습니다.
화면을 두 개 만들거나, 하나로 처리하거나.

저는 **하나로 갔습니다.**
순위표 컴포넌트는 하나만 두고, **"몇 등이 어디에 해당하는가"를 데이터로** 뺐습니다.
리그면 4위까지 파란색, 챔피언스리그면 8위까지 파란색.
컴포넌트는 그 규칙을 읽기만 합니다.

이렇게 하면 나중에 리그가 늘어도 화면은 안 건드립니다.

[선택 — 시간 있으면]
그리고 구역 표시를 색깔만으로 하지 않았습니다.
왼쪽에 색 막대를 넣고, 배경에 옅은 색을 깔고, 아래에 범례 텍스트를 붙였습니다.
색을 구분 못 하는 사람도 알 수 있어야 하니까요.

## 4. 화면은 네 가지 얼굴을 가진다 · 1분 20초

[상태 4종 그림 띄우고]

데이터를 보여주는 화면은 사실 하나가 아닙니다. 네 개입니다.

로딩 중일 때, 오류가 났을 때, 결과가 없을 때, 그리고 정상일 때.
저는 이걸 **각각 다 만들었습니다.**

[여기가 핵심 — 강조]

왜 굳이 그랬냐면, 이전 프로젝트에서 사고가 있었습니다.

오류가 났을 때 그냥 빈 배열로 바꾸는 코드가 **스무 군데** 있었습니다.
그래서 백엔드가 죽어도 화면은 멀쩡하게 떴습니다.
"데이터 없음"이라고요.

[한 박자]

**아무 문제 없어 보이는데 서버가 죽어 있는 겁니다.**
이게 제일 위험한 실패입니다. 아무도 모르니까요.

그래서 이번엔 규칙으로 못박았습니다.
**오류를 빈 데이터로 바꾸지 않는다.**
오류는 오류 화면으로, 결과 없음은 결과 없음 화면으로 보여줍니다. 다르게 생겼습니다.

그리고 이걸 코드 검사에도 넣었습니다.
오류를 조용히 삼키는 코드가 새로 들어오면 **빌드가 멈춥니다.**

## 5. 현재 상태와 다음 · 1분

[정직하게]

지금까지 만들어진 걸 말씀드리면,
**화면 13개, 대회 6개, 한국어와 영어, 밝은 테마와 어두운 테마**입니다.

검사 결과는 이렇습니다.
데이터 검증 통과, 다국어 검사 통과, 코드 검사 통과.

접근성도 측정했는데, 여기서 하나 말씀드리고 싶은 게 있습니다.

[강조]

처음부터 통과한 게 아닙니다.
브라우저에서 실제로 측정해보니 **열한 군데가 기준 미달**이었습니다.
배지 글자색, 입력창 테두리, 포커스 표시.
눈으로는 멀쩡해 보였는데 수치로는 부족했습니다.
전부 고치고 다시 측정해서 지금은 통과합니다.

다음 단계는 두 가지입니다.

첫째, **디자인을 다시 합니다.**
지금 화면은 구조를 확인하려고 만든 것이라, 디자인 시스템을 새로 잡고 있습니다.

둘째, **백엔드가 붙으면 가짜 데이터를 걷어냅니다.**
그때 검사 스크립트는 그대로 두고 대상만 진짜 데이터로 바꿉니다.

감사합니다.

# 선택 블록 — 시간이 남으면

## D. 화면 13개를 어떻게 정했나 · 1분

[화면 지도 그림이 있으면 여기서]

화면을 기능이 아니라 **사용자가 뭘 하러 왔는지**로 묶었습니다.

세 가지가 나왔습니다.
"지금 뭐 하고 있지", "우리 팀 어떻게 됐지", "누가 제일 잘하지".

이 중에 첫 번째가 **압도적으로 잦습니다.**
그래서 홈 화면은 이것만을 위해 만들었습니다.
들어오자마자, 스크롤 없이, 지금 진행 중인 경기가 보이게요.

나머지 두 개는 들어가는 입구만 확실히 두면 됩니다.

[여기가 포인트]
화면 개수를 세는 대신 동선으로 묶으니까, **어디에 시간을 쓸지**가 정해졌습니다.

## E. 다국어를 두 층으로 나눈 이유 · 1분 30초

한국어와 영어를 지원하는데, 번역해야 하는 게 두 종류입니다.

하나는 **UI 문구**입니다. "순위", "오늘의 경기", "전체 보기" 같은 것들이요.
다른 하나는 **고유명사**입니다. 맨체스터 시티, 손흥민, 프리미어리그.

이 둘을 같이 관리하면 깨집니다. 성격이 완전히 다르거든요.

UI 문구는 제가 정하면 끝입니다. 화면에만 쓰이니까요.
그런데 팀 이름은 다릅니다.
**영어 원본을 보존해야 하고**, 검색할 때 한국어로도 영어로도 찾을 수 있어야 합니다.
그리고 새 선수가 들어오면 한국어 이름이 없는 상태가 생깁니다.

그래서 **UI 문구는 프론트, 고유명사는 백엔드**로 나눴습니다.

지금은 백엔드가 없어서 고유명사도 프론트에 임시로 표를 두고 있는데,
임시라는 걸 알고 만든 거라 **검사 스크립트가 "이 선수는 한국어 이름이 없다"고 경고**해줍니다.
지금 여섯 명이 걸려 있습니다.

[선택]
그리고 번역 누락은 눈으로 못 찾습니다.
영어로 바꿨을 때만 드러나는 한국어가 화면 어딘가에 남아 있거든요.
그래서 검사 중 하나가 **소스 코드에서 한국어 글자를 직접 찾습니다.**
번역 파일이랑 가짜 데이터는 빼고요.

# 예상 질문

**Q. 왜 프론트를 먼저 만들었나요?**
→ 화면을 그려봐야 백엔드가 무엇을 줘야 하는지 정해지기 때문입니다.
실제로 순위표를 만들면서 "진출권 판정은 화면이 아니라 서버가 해야 한다"는 결론이 나왔습니다.

**Q. 지금 보이는 데이터는 진짜인가요?**
→ 아닙니다. 전부 제가 만든 가짜 데이터입니다.
다만 가짜여도 규칙은 맞아야 해서, 승점 계산이나 순위 정렬을 검사하는 스크립트를 따로 돌립니다.

**Q. 백엔드가 붙으면 뭘 바꿔야 하나요?**
→ 데이터를 가져오는 계층 하나만 바꿉니다.
지금도 화면이 데이터를 직접 들고 있지 않고 그 계층을 통해서만 받게 해뒀습니다.
그리고 팀·선수 한국어 이름 표를 지우고 서버가 주는 이름을 씁니다.

**Q. TypeScript를 안 쓴 이유가 있나요?**
→ 제가 직접 이해하고 수정할 수 있는 구성을 우선했습니다.
대신 데이터 형태가 틀어지는 걸 막으려고 검증 스크립트를 만들었습니다.
타입 검사 대신 데이터 검사를 하는 셈입니다.

**Q. 반응형은 어디까지 됐나요?**
→ 1440과 390 두 폭에서 가로 넘침이 없는 것까지 확인했습니다.
가장 어려운 건 순위표인데, 열이 11개라 모바일에 안 들어갑니다.
순위와 팀 이름 열을 고정하고 나머지를 가로로 스크롤하게 했습니다.

**Q. 디자인을 다시 한다고 했는데, 지금 것은 버리나요?**
→ 화면 구조와 데이터 흐름은 유지하고, 시각적인 부분을 다시 합니다.
색과 간격 같은 기준을 먼저 정하고 있고, 그게 끝나면 화면에 적용합니다.

# 전체 발표 구성 (백엔드 + 프론트)

| 순서 | 내용 | 시간 |
|---|---|---|
| 백엔드 0~5 | 오프닝 · 왜 어려운가 · 기술 선택 · 구조 · 종료≠확정 · 현재 상태 | 7분 30초 |
| 프론트 0~5 | 순서를 뒤집었다 · 가짜 데이터 검사 · 두 형식 · 상태 4종 · 현재 상태 | 6분 |
| **핵심 합계** | | **13분 30초** |
| 선택 블록 A~E | 5개 | 최대 +7분 |

**15분 발표면** 핵심만. **20분이면** 선택 블록에서 B(실패 처리)와 E(다국어)를 추가하세요.
