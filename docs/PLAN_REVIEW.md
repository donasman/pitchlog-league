## 0. 한 줄 요약

기획의 뼈대(외래키 없음 · 컷오프 규칙 · 조용한 실패 금지 · 수집 계층 L0~L6)는 코드가
그대로 따랐고 실측이 검증했다. 어긋난 곳은 세 군데다.

1. **배포 전략이 무효다** — `V2_DESIGN` 4장은 Next.js 정적 빌드 전제인데 프론트는 09-01 에 Vite SPA 로 바뀌었다. "배포 PoC" 가 검증하려는 것이 이제 존재하지 않는다.
2. **프론트가 발표용 고정 시계로 만들어져 있다** — "오늘" 이 `2026-11-23` 으로 세 곳에 박혀 있다. 다음 단계(경기·순위 실 API)에서 바로 부딪힌다.
3. **제품 차별점에 데이터 모델이 없다** — `final → recheck → confirmed` 는 PRD 가 "존재 이유" 라고 부르는데 스키마에 컬럼이 없다. 경기 DTO 를 정하는 순간 결정이 필요하다.

그리고 실측이 계획을 **네 번** 뒤집었다(로고 · 백업 · L1 동시 등장 · UCL 컷). 넷 다 "돌려보기 전엔 안 보이는 것" 이었다. 이 사실이 순서 변경안의 근거다 — 설계를 더 하는 것보다 **얇게 끝까지 연결해서 돌려보는** 쪽이 남은 위험을 더 빨리 드러낸다.

## 1. 기획안에서 바뀐 전제 — 문서가 따라오지 못한 것

| 전제 | 기획 당시 | 지금 | 문서 상태 |

| 프론트 스택 | Next.js + TS (`V2_DESIGN` 4장 전체) | **React + Vite + JS** (09-01) | `FRONTEND_GUIDE` 만 갱신. `V2_DESIGN` 4장 · `NEXT_STEPS` 2장 배포 PoC 항목은 Next.js 용어 그대로 |
| 범위 | 6대회 단일 시즌 → EPL 로 시작 | 12대회 × 5시즌 (09-04·06) | 반영됨 |

### 1-1. 배포 전략 — 검증할 대상이 사라졌다

`V2_DESIGN` 4-2 는 "A. 정적 + 전량 CSR 은 **배제한다** — SEO 손실이 서비스 존재 이유와 충돌"
이라 썼고, B안(정적 + 빌드 훅)을 골라 PoC 5항목을 정했다:
5,000페이지 정적 빌드 시간 · Deploy Hook 지연 · `generateStaticParams` throw · `deployment_requests` 디바운스.

**Vite SPA 는 정확히 A안이다.** `generateStaticParams` 도 ISR 도 빌드 훅으로 다시 만들 페이지도 없다.
`FRONTEND_GUIDE` 7장은 이걸 알고 "SEO 는 공개 전 별도 결정" 으로 미뤄뒀다. 그런데 `NEXT_STEPS` 2장은
여전히 "배포 PoC (PR #6) — 정적 빌드 시간, Deploy Hook 지연, Socket.io 연결" 이다.
**존재하지 않는 것을 검증하는 항목이 Phase 0 의 마지막 관문으로 남아 있다.**

실제로 필요한 배포 확인은 훨씬 작다:

| 항목 | 왜 |
|---|---|
| 백엔드 상시 호스팅 (Railway Hobby 등) | Pages 에 올린 프론트는 `localhost:3000` 을 못 본다. **프론트만 배포하면 지금보다 더 안 나온다** |
| Supabase ↔ 호스팅 연결 · 환경변수 · `CORS_ORIGIN` | 이미 코드에 있다. 값만 맞추면 된다 |
| Pages SPA fallback (`/*` → `index.html`) | `FRONTEND_GUIDE` 9장 |
| 로고 정적 경로 (`/logos/…`) | 저장소 안이라 Pages 가 그대로 서빙 |

"늦을수록 배포 제약이 코드에 반영될 기회를 잃는다" 는 논거는 정적 빌드 제약(페이지 수 · 빌드 시간 · 빌드 시점 백엔드 의존)을 두고 한 말이다. **그 제약이 사라졌으니 논거도 약해졌다.** 남은 제약은 CORS 와 환경변수뿐이고 이미 코드에 있다.

SEO 는 별개 문제로 남는다. `FRONTEND_GUIDE` 7장의 4가지 선택지(프리렌더 · 사이트맵 · Edge 메타 · SSR 재검토)는 공개 전에 정하면 된다. 지금 정할 필요는 없지만 **"정하지 않았다" 를 문서 한 곳에서 계속 보이게** 두어야 한다.

## 2. 다음 단계에서 바로 부딪히는 것

다음 작업은 "조회 API 확장(경기·순위) + 프론트 연결" 이다. 이 셋은 그 작업 안에서 만난다.

### 2-1. 프론트의 시계가 멈춰 있다

발표용으로 만든 흔적이다. 주석에 그렇게 적혀 있다.

| 위치 | 고정값 | 영향 |
|---|---|---|
| `pages/MatchesPage.jsx` `MOCK_TODAY` | `2026-11-23` | "오늘" 태그 |
| `pages/TeamFixturesPage.jsx` `MOCK_TODAY_KST` | `2026-11-23` | 과거/오늘/미래 분리 |
| `utils/matchSort.js` `filterTodayMatches` | `2026-11-23` | ISO 문자열 **접두 비교** — UTC 날짜다. KST 23:00 이전 경기는 전날로 간다 (지금은 미사용) |
| `utils/dateFormat.js` `calcAge` | `2026-09-01` | 선수 나이. 게다가 L1 이 받는 squads 에는 생년월일이 없다 → `new Date(null)` = 1970 → **56세** |
| `getKSTDateKey` | 두 페이지에 **각각** 복사돼 있다 | util 이 아니라 페이지 안에 있어 테스트 대상이 아니다 |

실 데이터를 붙이면 경기 목록의 "오늘" 이 11월 23일을 가리킨다.

이건 회고 3장이 지목한 v1 사고 그대로다 — **KST/UTC 변환 fix 가 3회 반복됐고**, 회고 4-5 와 `V2_DESIGN` 7-1 은 "처음부터 테스트를 넣는다" 고 약속했다. **프론트 테스트는 0개다.** `frontend/package.json` 에 테스트 러너가 없다 (`playwright` 만 있고 스크린샷 대조용이다).

필요한 것: 시계를 한 곳으로 모은다(`services/clock.js` 같은 것 — Mock 모드는 고정, 실 API 모드는 `new Date()`), `getKSTDateKey` 를 util 로 올리고, 이 셋에 단위 테스트를 붙인다. 프론트 연결 PR 에 같이 들어가야 한다. 따로 하면 안 된다.

### 2-2. `recheck → confirmed` 에 컬럼이 없다

PRD 4-2: "`final` 과 `confirmed` 는 다른 상태다. 그 사이가 `recheck` — **이 서비스의 차별점**이므로 시각적으로 드러낸다."
`BACKEND_FEATURES` #34 "`recheck → confirmed` 상태 전이" 가 있다. 그런데 `matches` 에는 API 상태(`status_short`)와 상세 유무(`has_*` · `detail_checked_at`)만 있고 **"통계가 확정됐는가" 를 담는 컬럼이 없다.**

프론트는 Mock 이 `displayState: 'recheck'` 를 직접 주니까 그려진다. 실 API 로 넘어가면 `normalize.js` 가 무엇으로 `recheck` 를 만들어야 하는지 정의가 없다.

이건 L4·L5 문제처럼 보이지만 **경기 DTO 에 `displayState` 를 싣는 순간** 답을 내야 한다. 선택지:

| 안 | 내용 | 비용 |
|---|---|---|
| a | 지금은 `FT` = `final` 로만 보내고 `recheck`·`confirmed` 는 프론트에서 안 나오게 둔다 | 0. 차별점이 실 API 모드에서 잠시 사라진다 |
| b | `matches.stats_state` (`NONE` · `RECHECK` · `CONFIRMED`) + `confirmed_at` 을 지금 추가. L2 는 `NONE`, L5 가 `RECHECK`→`CONFIRMED` 로 올린다 | 마이그레이션 1개. L5 설계가 컬럼 하나를 미리 갖는다 |
| c | `has_player_stats = true AND has_team_stats = true` 를 `confirmed` 로 **파생** | 컬럼 없음. 단 "확인했고 없음(false)" 인 컵 경기는 영원히 `recheck` 다 — 3값 논리와 충돌 |

### 2-3. 홈은 L2 만으로 안 산다

PRD 는 홈(동선 A "지금 뭐 하고 있지")을 P0 첫 번째로 둔다. 홈 첫 화면 6블록 중:

| 블록 | 필요한 계층 | 지금 |
|---|---|---|
| 대회 칩 · 오늘의 경기 · 최근/다음 경기 | L2 | **있다** |
| 요약 스트립(진행 중 경기 수) · LIVE 히어로 | L4 라이브 | 없음 |
| 순위 Top5 | L2 순위 | **있다** |
| 득점 Top5 · EPL 득점 1위 | L6 선수 시즌 통계 | 없음 |
| UCL 녹아웃 진출 팀 | L2-b | 2027-02 |

"오류를 빈 데이터로 바꾸지 않는다" 규칙이 여기서 시험된다. 없는 블록은 **블록 단위로 `NotImplemented`** 를 보여야지, 홈 전체를 막거나 빈 카드를 그리면 안 된다. `EmptyState` 에 `action` prop 이 없는 것(`NEXT_STEPS` 7장, 1단계 감사 #11 이후 방치)도 여기서 걸린다.

## 3. 계획 문서와 코드가 다른 것

### 3-1. 한국어 이름 — 만들 사람이 없다

PRD 3장 · 4-5: 한국어·영어 전환은 핵심 기능이고 "팀명이 들어가는 모든 셀" 이 영향받는다.
`FRONTEND_GUIDE` 13-2: "자동 음역만으로 생성하지 않으며 **주요 선수부터 검수된 이름**을 적용."
`localized_names` 테이블은 있다. **채우는 코드도, 소스도, 담당도 없다.** 대상은 팀 1,888 · 선수 4,863.

지금 실 API 모드의 언어 전환은 메뉴·버튼만 바뀌고 팀·선수 이름은 영어 그대로다.
PRD 가 약속한 것과 다르다. 범위를 정해야 한다:

| 안 | 범위 | 비용 |
|---|---|---|
| a | 화면 6대회 참가팀 **96 + 리그페이즈 14 = 110팀** 만 한국어. 선수는 영어 | 팀 110개 손 입력. 반나절 |
| b | a + 5대 리그 주전급 선수 (팀당 15명 ≈ 1,500명) | 검수가 병목. 소스가 없다 |
| c | 팀만 하고 선수 한국어는 **범위에서 뺀다** 고 PRD 에 명시 | 0. 정직하다 |

어느 쪽이든 **`localized_names` 를 채우는 경로(CSV 적재 CLI 같은 것)가 필요**하고, 지금은 없다.

### 3-2. 테스트 약속 — 백엔드는 지켰고 프론트는 안 지켰다

`V2_DESIGN` 7-1 의 "처음부터 쓰는 테스트" 7개:

## 4. 흐름 · 순서에서 걸리는 것

### 4-1. 스케줄러가 0 이다

모든 수집이 `npm run ingest -- lN` 수동이다. L2 순위표는 **경기일마다** 다시 받아야 맞고,
L1 은 주 1회다. 어디에 배포하든 사람이 명령을 안 치면 그 순간부터 낡는다.

`@nestjs/schedule` 은 **이미 의존성에 있다.** Redis 가 필요 없다. L2 매일 1회 · L1 주 1회 ·
`/status` 매일 1회 — 크론 셋이면 된다. "배포" 앞에 와야 한다. 배포한 사이트가 낡은 순위표를 보여주면 v1 의 placeholder 사고와 같은 종류의 조용한 실패다.

### 4-2. 백필의 자리

`INGESTION_STRATEGY` 5-3 "최신 시즌부터 역순. 1일차에 2026 시즌이 완성되면 사이트를 열 수 있다" —
이 문장이 백필 = 사이트 개통 조건처럼 읽힌다. 그런데 **2026 시즌 일정·순위는 L2-a 로 이미 있다.**
백필이 화면에 주는 것은 두 가지뿐이다: 시즌 선택기(2022~2025) · 현재 시즌 **상세**(라인업 · 이벤트 · 통계 = L3~L5 를 과거 경기에 소급).

완성도 순으로 보면 **현재 시즌의 L3~L5 가 과거 4시즌보다 먼저**다. 경기 상세(P0)와 통계(P1)가 그걸로 산다. 백필은 그 코드가 검증된 뒤 같은 코드를 과거로 돌리는 일이라 뒤로 미뤄도 손해가 없고, 오히려 L3~L5 가 현재 시즌에서 한 번 검증된 뒤 백필하는 편이 8~12일을 두 번 쓰지 않는다.

### 4-3. 라이브(L4)의 자리

PRD 동선 A 가 "압도적" 이고 홈이 그걸 위해 최적화돼 있다. 그런데 수집 계층 순서는 L2 → 백필 → L3 → L4 → L5 라 **가장 중요한 화면의 핵심이 가장 뒤**다. `live=all` 1콜 · 10초 폴링 · 윈도우 개폐 — 예산 계산은 `INGESTION_STRATEGY` 6장에 이미 있다. 스케줄러(4-1)가 생기면 그 위에 얹는 첫 잡이 될 수 있다.

### 4-4. 그냥 하면 되는데 안 한 것

| 항목 | 비용 |
|---|---|
| L1 두 번째 실행 — diff 가 실 데이터에서 한 번도 안 돌았다 | 155콜, 몇 분 |
| UCL 예선 전용 팀 걷어내기 — L2-a 로 기준이 생겼다("저장된 경기에 없는 팀") | SQL 하나 + L1 범위 조건 |
| `EmptyState` `action` prop | 10줄 |
| `frontend/README.md` | 10분 |

### 4-5. 측정이 계획을 네 번 바꿨다

| 계획 | 실측 | 바뀐 것 |
|---|---|---|
| 로고 직링크, 폴백 있으니 됨 | 96장 영원히 로딩, `onError` 안 불림 | 자체 저장을 백필 앞으로 |
| 백업 스크립트면 됨 | 리허설이 4건 잡음 (내부 스키마 · 데몬 · public 충돌 · 로그) | 리허설이 관문 |
| 두 팀 동시 등장은 API 이상 | 이적 중 실제 상황 | throw → 보류 |
| UCL 컷은 리그페이즈 | 리옹이 Q3 | 예측이 틀리고 코드가 맞음 |

공통점: **설계 검토로는 안 잡히고 돌려봐야 잡혔다.** 남은 위험(L4 폴링 · Socket · 확정 처리 · 백필 8일)도 같은 성격이다. 이게 "설계 문서를 더 다듬기" 보다 "얇게 끝까지 연결" 을 권하는 이유다.

## 5. 순서 변경안 — 선택지

### 안 A. 얇게 끝까지 (완성도 우선)

```
1. 조회 API 경기·순위 + 프론트 3화면(경기 목록·상세·순위·대회 허브)
   └ 같은 PR 에: 시계 통일(2-1) · recheck 결정(2-2) · 홈 블록별 결손(2-3) · 프론트 vitest 첫 3건
2. 스케줄러 최소 3잡 (L2 매일 · L1 매주 · status) — Redis 없이
3. 배포 = 백엔드 호스팅 + Pages + CORS (재정의된 PoC, 1-1)  ← 여기서 처음 "남에게 보여줄 수 있는" 상태
4. L4 라이브 폴링 → 홈 LIVE 히어로
5. L3·L5 현재 시즌 → 경기 상세 탭
6. 백업 자동화 · 사본 이중화 · 리허설 재실행
7. 백필 (L2-b 포함)
8. L6 · 한국어 이름 · 알림 · AI
```

얻는 것: 3번 시점에 살아 있는 사이트. 각 단계가 앞 단계를 실 데이터로 검증한다.
잃는 것: L1 #9~#11(프로필 · 감독 · 부상)이 뒤로 간다. 문서 Phase 표를 다시 쓴다.

### 안 B. 문서 순서 유지

```
배포 PoC(재정의) → L1 #9~#11 → 백업 자동화 → 백필 8~12일 → L3~L5 → 프론트 연결
```

얻는 것: 문서 안 고침. 백필이 일찍 끝나 시즌 선택기가 산다.
잃는 것: 백필 8~12일 동안 화면은 지금 그대로(2/12). 백필이 도는 동안 L3~L5 코드를 못 검증하고, 끝난 뒤 L3~L5 를 만들면서 백필한 상세 데이터 형태가 틀린 걸 발견하면 다시 돈다.

### 안 C. 절충

안 A 의 1~3 을 먼저 하고(사이트를 연다), 그다음 안 B 로 돌아가 백필을 돌리면서 **병렬로** L4 를 만든다. 백필은 콜 예산을 쓰지만 사람 손은 안 쓰므로 L4 작업과 겹칠 수 있다. 단 백필 중 L1 락(`SCHEMA_DESIGN` 충돌 ③) 때문에 스케줄러 L1 잡은 락을 봐야 한다 — 이미 코드에 있다.
