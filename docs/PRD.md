# PitchLog PRD — 화면 요구사항

> 작성: 2026-09-03 · 상태: 초안  
> 범위: **화면 중심**. 도메인 모델·수집·배포는 [`V2_DESIGN.md`](./V2_DESIGN.md),
> 백엔드는 [`BACKEND_GUIDE.md`](./BACKEND_GUIDE.md), 프론트 기술 기준은
> [`FRONTEND_GUIDE.md`](./FRONTEND_GUIDE.md)를 따른다. 이 문서는 그 위에서
> **"어떤 화면이 무엇을 보여줘야 하는가"** 만 정의한다.
>
> 사용처: Claude Design 레이아웃 작업의 입력. 디자인 단계에서 판단이 필요한 것만 담고,
> 구현 방식(컴포넌트 이름, 클래스, 라이브러리)은 의도적으로 적지 않는다.

---

## 1. 제품 정의

**유럽 5대 리그와 UCL의 경기·순위·선수 기록을, 근거와 기준 시각을 함께 보여주는 축구 데이터 서비스.**

경쟁 서비스와의 차이는 속도가 아니라 **신뢰성 표기**다. 진행 중인 경기의 숫자는 임시값이고
경기 종료 후 공식 통계로 재확정된다는 사실을, 숨기지 않고 화면에 드러낸다.

### 하는 것

- 6개 대회의 경기 일정·결과·진행 상황
- 순위표와 승격/강등·UCL 진출 구역
- 선수·팀 시즌 기록과 대회별 분리 조회
- UCL 리그 페이즈와 녹아웃 대진(1·2차전 합산)
- 한국어·영어 전환

### 지금 안 하는 것

| 항목 | 사유 |
|---|---|
| 로그인·회원 기능 | 개인화 요구가 아직 없음. 즐겨찾기는 로컬 저장으로 대체 |
| 배당·베팅 정보 | AdSense 정책 리스크로 보류 (V2_DESIGN 부록) |
| AI 챗봇 패널 | Phase 5. 단 **진입 지점 자리는 지금 레이아웃에서 비워둔다** |
| 관리자 화면 | 별도 동선. 이번 디자인 범위 밖 |
| 부상자 목록(`/injuries`) | 라우트는 설계에 있으나 현재 미구현. 2차 |

### 성공 기준 (디자인 단계)

1. 처음 방문한 사람이 **스크롤 없이** 오늘 무슨 경기가 있는지 안다 (1440×900 기준)
2. 진행 중인 경기와 확정된 경기를 **색상 없이도** 구분할 수 있다
3. 순위표에서 "이 팀이 어디로 가는지"(UCL 진출/강등)를 한눈에 안다
4. 한국어↔영어 전환에서 레이아웃이 깨지지 않는다

## 2. 사용자와 핵심 동선

명시적 페르소나 조사는 없다. 실제 사용 맥락에서 도출한 3가지 동선만 둔다.

| # | 동선 | 시작점 | 끝점 | 빈도 |
|---|---|---|---|---|
| **A** | "지금 뭐 하고 있지" | `/` | 진행 중 경기 카드 → `/matches/:id` | 가장 높음 |
| **B** | "우리 팀 어떻게 됐지" | `/` 또는 검색 | `/teams/:slug` → `/teams/:slug/fixtures` | 높음 |
| **C** | "누가 제일 잘하지" | `/stats` 또는 홈 사이드바 | `/players/:slug` | 중간 |

동선 A가 압도적이므로 **홈은 A를 위해 최적화하고, B·C는 진입 지점만 확실히 제공**한다.

한 팀이 국내 리그와 UCL에 동시에 참가하므로, B 동선에서는 **대회 필터가 기본 요구사항**이다.

## 3. 전제

| 항목 | 값 |
|---|---|
| 대회 | EPL, 라리가, 분데스리가, 세리에 A, 리그 1, UCL — **6개 동시** |
| 시즌 | 단일 시즌(26–27) 우선. 시즌 선택기는 자리만 확보 |
| 언어 | 한국어·영어. 기본값은 브라우저 설정, 선택은 저장됨 |
| 테마 | 라이트·다크 **양쪽 필수**. 시스템 설정 추종 + 수동 고정 |
| 데이터 | 현재는 Mock. 화면은 실 API 연결 시 구조가 바뀌지 않도록 설계 |
| 기준 해상도 | 데스크톱 1440×900, 모바일 390×844 |

> ⚠️ UCL은 국내 리그와 **형식이 다르다.** 조별리그가 아니라 리그 페이즈(단일 순위표)이고,
> 녹아웃은 1·2차전 합산이다. 순위표·경기 목록·대회 허브는 이 두 형식을 **같은 레이아웃에서
> 전환**할 수 있어야 한다. 별도 화면을 만들지 않는다.

## 4. 전역 규칙 — 모든 화면이 지킨다

### 4-1. 화면 상태 4종

모든 데이터 화면은 아래 4가지를 **각각 다른 화면으로** 가진다. 디자인 시 4개 모두 그린다.

| 상태 | 규칙 |
|---|---|
| 로딩 | 스켈레톤. 실제 콘텐츠와 같은 높이·개수여야 레이아웃이 튀지 않는다 |
| 오류 | **빈 화면으로 위장 금지.** 무엇이 실패했는지와 재시도 수단을 보여준다 |
| 빈 결과 | 오류와 시각적으로 구분된다. "필터를 바꿔보라"는 다음 행동을 제시 |
| 정상 | — |

"오류를 빈 데이터로 바꾸지 않는다"는 v1 사고의 재발 방지책이며 타협 대상이 아니다.

### 4-2. 경기 상태 8종

`scheduled` · `live` · `halftime` · `final` · `recheck` · `confirmed` · `postponed` · `cancelled`

- `live`/`halftime`은 **깜빡임 또는 도트 등 색상 외 단서**를 함께 갖는다
- `final`(경기 종료)과 `confirmed`(공식 통계 확정)는 **다른 상태**다.
  그 사이가 `recheck`(재검증 중, 숫자가 바뀔 수 있음) — 이 서비스의 차별점이므로 시각적으로 드러낸다
- 배지는 **한 줄을 유지**한다. 한국어·영어 모두에서 줄바꿈되면 안 된다

### 4-3. 순위 구역 표기

국내 리그: UCL 직행 / UEL / 컨퍼런스리그 / 강등 플레이오프 / 강등  
UCL 리그 페이즈: 16강 직행 / 플레이오프 / 탈락

- **색상 단독 금지.** 좌측 표시선 + 행 배경 틴트 + **범례 텍스트** 3종을 함께 쓴다
- 범례는 표 하단에 항상 노출한다 (접어두지 않는다)

### 4-4. 숫자

승점·득실차·순위·스코어는 **고정폭 숫자**를 쓴다. 자릿수가 바뀔 때 열이 흔들리면 안 된다.

### 4-5. 다국어

- 한국어→영어 전환 시 **팀 이름이 길어진다** (예: 뉴캐슬 → Newcastle United).
  팀명이 들어가는 모든 셀은 넘침 처리 기준을 정한다 (말줄임 / 축약명 전환 / 줄바꿈 중 택1)
- 대회명·팀명·선수명은 축약형(`EPL`, `NEW`)과 전체형 두 가지가 필요하다
- 언어 전환은 **즉시 반영**되고 새로고침 후에도 유지된다

### 4-6. 접근성 (Foundation 감사에서 확정된 기준)

| 항목 | 기준 |
|---|---|
| 본문 텍스트 대비 | 4.5:1 이상 |
| 큰 텍스트(18.66px/700+) | 3:1 이상 |
| 입력·컨트롤 경계 | 3:1 이상 |
| 포커스 표시 | 모든 인터랙티브 요소에 `:focus-visible` 외곽선 + offset |
| 상태 구분 | 색상 단독 금지 (4-2, 4-3) |
| 애니메이션 | `prefers-reduced-motion`에서 정지 |

`design/pitchlog-base-tokens.css`에 검증된 토큰이 있다. **새 색을 만들기 전에 그 토큰을 먼저 본다.**

### 4-7. URL 상태 보존

대회·시즌·팀·탭 선택은 **URL 검색 파라미터에 남는다.** 새로고침하거나 링크를 공유해도
같은 화면이 복원된다. 디자인 시 "이 필터가 URL에 남을 값인가"를 판단해 표시한다.

## 5. 전역 요소

| 요소 | 요구사항 |
|---|---|
| 헤더 | 로고, 주 메뉴(경기·순위·팀·통계), 검색, 언어 토글, 테마 토글. 모바일에서는 메뉴 접기 |
| 검색 | 팀·선수·대회 통합. 한국어·영어 양쪽으로 검색된다. 오버레이 또는 패널 |
| 대회 선택기 | 6개 대회 + "전체". **홈과 목록 화면에서 반복 등장하는 핵심 컨트롤**이므로 일관된 형태를 하나만 만든다 |
| 데이터 기준 시각 | 숫자를 보여주는 모든 블록에 "언제 기준인지"를 작게 표기 |
| AI 패널 진입점 | Phase 5용 자리. 지금은 위치만 확보하고 그리지 않아도 된다 |
| 푸터 | 데이터 출처 표기(API-Football), 면책 문구 |

## 6. 화면별 명세

우선순위 표기: **P0** = 이번 디자인 필수 · **P1** = 이어서 · **P2** = 자리만

### 6-1. 홈 `/` — P0

동선 A의 전부. **가장 중요한 화면이고 가장 먼저 그린다.**

첫 화면(1440×900, 스크롤 전)에 들어가야 하는 것:

1. **대회 필터 칩** — 6개 대회 다중 선택 + 전체
2. **요약 스트립** — 진행 중 경기 수 / 오늘 경기 수 / EPL 선두 / EPL 득점 1위
3. **LIVE 히어로 카드** — 진행 중 경기 1건을 크게. 없으면 다음 예정 경기로 대체
4. **보조 경기 카드 2건**
5. **오늘의 경기 목록** — 최대 8행
6. **사이드바** — 대회 선택기 + 순위 Top5 + 득점 Top5 + UCL 녹아웃 진출 팀

스크롤 아래: 최근 결과 / 다음 경기 / UCL 16강 3열.

레이아웃: 본문 + 사이드바 2열. 사이드바는 고정폭, 본문 가변. 모바일에서는 사이드바가 본문 아래로.

> 사이드바의 대회 선택기는 상단 필터 칩과 **독립적으로 동작**한다.
> (상단 = 경기 목록 필터, 사이드바 = 순위·득점 대회 선택) 디자인에서 이 둘이
> 같은 컨트롤로 오해되지 않도록 시각적으로 구분한다.

### 6-2. 순위 `/standings` — P0

이 서비스에서 **정보 밀도가 가장 높은 화면**. 레이아웃 난이도도 가장 높다.

- 대회 선택 + 시즌 선택
- 순위표: 순위, 팀, 경기수, 승, 무, 패, 득점, 실점, 득실차, 승점, 최근 5경기 폼
- 구역 표기(4-3) + 하단 범례
- 스테이지 표기 — UCL은 "리그 페이즈 4라운드 진행 중" 같은 진행 상태를 함께
- 데이터 기준 시각

**모바일이 진짜 문제다.** 11개 열이 390px에 안 들어간다.
→ 순위·팀 열을 고정(sticky)하고 나머지를 가로 스크롤. 가로 스크롤이 가능하다는 **안내를
명시적으로 표시**한다. 폼 배지는 모바일에서 숨기거나 축약한다.

### 6-3. 경기 목록 `/matches` — P0

- 필터: 대회, 시즌, 팀, 라운드/스테이지, 날짜
- 날짜별 그룹핑
- 각 행: 시간(KST), 대회 표시, 홈–원정, 스코어 또는 예정 시각, 상태 배지
- UCL은 라운드 대신 스테이지(리그 페이즈 / 플레이오프 / 16강…) 선택

필터가 4개 이상이므로 **필터 바 자체의 모바일 처리**를 함께 설계한다 (접기 / 바텀시트 / 칩 스크롤).

### 6-4. 경기 상세 `/matches/:fixtureId` — P0

- 상단: 두 팀, 스코어, 상태 배지, 대회·라운드, 킥오프 시각, 경기장
- 탭: 라인업 / 통계 / H2H / 타임라인
- **UCL 전용**: 1·2차전 표기, 합산 점수, 진출 팀
- `recheck` 상태일 때 "이 숫자는 아직 확정 아님"을 명시

라인업은 포메이션 도면이 필요하다. v1 자산은 재사용하지 않고 새로 디자인한다.
**세로 배치(모바일)와 가로 배치(데스크톱) 두 가지가 필요하다.**

### 6-5. 대회 허브 `/competitions/:slug` — P1

한 대회의 모든 것으로 가는 관문. 탭 또는 섹션으로:

- 순위 요약 (Top 8 + 전체 보기)
- 이번 라운드 경기
- 득점·도움 Top 5
- 참가 팀 목록
- **UCL만**: 녹아웃 대진 진입 버튼

국내 리그와 UCL이 **같은 레이아웃에 다른 섹션 구성**으로 들어간다.

### 6-6. UCL 녹아웃 `/competitions/champions-league/knockout` — P1

플레이오프~결승 대진표. 가장 특이한 레이아웃.

- 각 타이: 두 팀, 1차전 스코어, 2차전 스코어, **합산 점수**, 진출 팀 표시
- 미확정 팀은 TBD
- 진행 상태: 예정 / 1차전 종료 / 완료

**대진표는 가로로 넓다.** 데스크톱은 라운드별 열 배치, 모바일은 라운드별 세로 아코디언 등
전혀 다른 레이아웃이 필요하다. 두 가지를 각각 그린다.

### 6-7. 통계 `/stats` — P1

- 대회 필터 (전체 합산 보기 포함)
- 득점 / 도움 / 카드 랭킹
- 각 행: 순위, 선수, 소속 팀, 수치
- 전체 합산 시 **대회별 분해(breakdown)** 표시 — 예: 12골 = EPL 9 + UCL 3

### 6-8. 팀 상세 `/teams/:slug` — P1

- 팀 정보: 엠블럼, 이름, 홈구장, 참가 대회
- 현재 순위 (대회별로 여러 개일 수 있음)
- 최근 경기 / 다음 경기
- 스쿼드 목록
- `/teams/:slug/fixtures`로 가는 링크

### 6-9. 팀 일정 `/teams/:slug/fixtures` — P1

동선 B의 종착점. **대회 필터가 핵심**이다 (전체 / 국내 리그 / UCL). 기본값은 전체.
과거·미래를 한 흐름으로 보여주되 "오늘" 위치를 표시한다.

### 6-10. 선수 상세 `/players/:slug` — P1

- 프로필: 사진, 이름, 등번호, 포지션, 소속 팀, 국적
- 시즌 기록 — **대회별 분리 + 전체 합산 토글**
- 출전, 골, 도움, 카드, 출전 시간

### 6-11. 대회 목록 `/competitions` — P2

## 9. 브랜드 컬러 후보

### 9-1. 문제 — 색은 이미 의미를 갖고 있다

순위표에서 파랑은 UCL 직행, 노랑은 UCL 플레이오프, 주황은 유로파, 초록은 컨퍼런스리그,
빨강은 강등이다. 여기에 상태색(정상 초록 / 주의 주황 / 오류·LIVE 빨강)까지 더하면
**파랑·초록·주황·빨강·노랑·회색이 전부 의미에 묶여 있다.**

현행 임시값 `#3366FF`는 UCL 직행 구역의 `blue-500`(`#3B82F6`)과 **색상환에서 8° 차이**다.
나란히 놓으면 브랜드 요소와 UCL 진출권이 같은 파랑으로 읽힌다. 교체가 필요한 이유다.

### 9-2. 후보 4안

대비는 WCAG 2.1 상대휘도 기준 실측값이다.
라이트는 `#FFFFFF`, 다크는 `#1E1E23` 위에서 측정했다.

| 안 | 색 | 이격 | 라이트 primary / hover / pressed | 다크 primary / hover / pressed |
|---|---|---|---|---|
| **A** | 바이올렛 | **34°** | `#6247D4` 6.23 / `#5439C4` 7.61 / `#4A31B0` 8.91 | `#A996FF` 6.71 / `#BCADFF` 8.35 / `#CCC0FF` 9.92 |
| B | 틸 | 32° | `#0A8074` 4.82 / `#077167` 5.89 / `#056055` 7.47 | `#4ECFBF` 8.70 / `#72DBCD` 10.06 / `#93E4D9` 11.33 |
| **C** | 마젠타 | 27° | `#C21D66` 5.74 / `#AC1259` 7.04 / `#96094D` 8.60 | `#FF7FB0` 7.05 / `#FF9CC2` 8.53 / `#FFB4D1` 10.04 |
| D | 현행 블루 | **8°** | `#3366FF` 4.68 / `#025FEB` 5.47 / `#0054D1` 6.59 | `#6E93FF` 5.75 / `#8FACFF` 7.52 / `#A0BAFF` 8.66 |

"이격"은 가장 가까운 의미색과의 색상환 거리다. 작을수록 순위표에서 혼동될 위험이 크다.

### 9-3. 판단

**A안(바이올렛) 권장.** 의미색과 34° 떨어져 순위표에서 브랜드와 구역이 섞이지 않고,
라이트 6.23:1 · 다크 6.71:1로 양쪽 모두 여유가 있다. 축구 데이터 서비스가 대부분
파랑·초록·빨강을 쓰므로 구별성도 확보된다.

- **A안의 유일한 걸림돌** — 보라는 프리미어리그의 상징색이다. 6개 대회를 다루는 서비스가
  한 리그의 색을 쓰는 것으로 읽힐 수 있다. 이게 걸리면 **C안(마젠타)** 이 대안이다
  (이격 27°, 어느 리그와도 무관). 단 빨강 계열이라 LIVE 배지와 톤이 겹칠 수 있어
  빨강을 쓰는 자리를 줄여야 한다.
- **B안(틸)은 권장하지 않는다.** 컨퍼런스리그 초록과 32° 차이지만, 실제 판단은 순위표의
  2px 좌측 표시선 같은 좁은 면적에서 이뤄지고 그 크기에서 청록과 초록은 잘 구분되지 않는다.
  라이트 대비 4.82:1도 네 후보 중 가장 낮다.

### 9-4. 확정 시 주의

1. **hover·pressed는 파생값이 아니다.** 위 값들은 명도만 낮춘 게 아니라 채도를 함께
   조정했다. 자동 계산으로 대체하지 않는다.
2. **다크는 반대로 밝아진다.** 라이트에서 hover가 어두워지는 것과 정반대이므로
   두 세트를 각각 정의한다.
3. `design/pitchlog-base-tokens.css`의 `--wds-primary` 3개와
   `design/pitchlog-theme-dark.css`의 다크 3개를 **함께** 교체한다. 한쪽만 바꾸면 테마가 어긋난다.
4. 다크 테마의 밝은 primary 위에는 흰 글자가 무너진다(2.5~2.9:1). `--pl-on-primary`로
   어두운 글자를 쓴다.
