## 확정된 우려사항 (4건 — 문서에 아직 없는 실제 공백)

### 1. [HIGH] 배치·스케줄러가 같은 행을 동시에 쓸 때의 안전장치가 없음
**관련 섹션**: 5-4, 1-1, 1-3, 1-5

문서 5-4는 "batch와 schedule이 서로를 호출하지 않고 같은 도메인 서비스를 부른다"는 구조로 v1의 양방향 결합을 해소한다고 설명합니다. 하지만 이건 **결합도 문제를 푸는 것**이지 **동시성 문제를 푸는 것**은 아닙니다. 시즌 초 스쿼드 백필(Batch)과 이적창 기간 매일 도는 스쿼드 diff(Schedule)가 같은 선수 row를 동시에 건드릴 수 있는데(여름 이적창 6/13~9/1은 실제로 시즌 개막과 겹칩니다), 실제 upsert가 `ON CONFLICT`인지 JPA `find-then-save`인지, 낙관적 락(`@Version`)을 쓰는지가 문서에 없습니다. `find-then-save`라면 예외 없이 조용히 값이 덮어써질 수 있는데, 이건 문서가 스스로 강조하는 "조용한 실패 금지" 원칙과 정면으로 충돌하는 지점입니다.

### 2. [HIGH] 5경기 동시 킥오프 검증이 API 호출 수만 확인했고, 처리량·상태전이는 안 됨
**관련 섹션**: 2-3, 3-2, 4-3

2-3에서 "동시 킥오프는 스케줄러 재설계 지점"이라고 스스로 짚어놓고, 뒤이은 3-2 검산은 API 호출 횟수(콜 수/예산)만 계산합니다. `live=all`이 1콜로 전 경기를 커버하는 건 맞지만, 그 1콜의 응답 페이로드는 동시 진행 경기 수에 비례해 커지고 이걸 파싱·upsert하는 처리 시간은 콜 수와 무관한 별개 변수입니다. `@Scheduled`가 처리 지연 시 오버랩 방지 장치(ShedLock 등)가 있는지, v1의 IDLE/LINEUP/LIVE 3단계가 "서로 다른 상태의 경기 5개"를 동시에 다룰 수 있는지도 언급이 없습니다. 필요조건(호출 예산)만 확인하고 충분조건(실제로 버티는가)은 검증되지 않았습니다.

### 3. [HIGH] 빌드 훅 디바운스/트리거에 영속 상태·멱등성이 없음
**관련 섹션**: 4-3, 5-3

5-3은 실시간 동기화(`@Scheduled`)를 "상태 불필요"로 명시적으로 설계합니다. 그런데 Deploy Hook은 "이미 이 라운드에 배포했는가"를 기억해야 중복 호출을 막을 수 있어, 이 요구사항 자체가 5-3의 무상태 설계 원칙과 충돌합니다. 서버 재시작으로 인메모리 디바운스 타이머가 사라지면 트리거가 조용히 유실되고(사이트가 갱신 없이 멈춤), 반대로 상태 관리 버그가 나면 반복 빌드가 발생할 수 있습니다. "월 500회 여유롭다"는 판단의 전제(주 10회 내외)가 최악 케이스로 검산되지 않았습니다.

### 4. [MEDIUM] SEO가 핵심 목표라면서 신규 라우트의 SEO 구현 스펙이 비어 있음
**관련 섹션**: 4-0, 6-1

문서는 "선수명+기록 검색 유입이 트래픽의 절대적 비중"이라 명시하고, `/teams/[slug]/fixtures`를 "검색 유입도 여기로 들어온다"며 신규 필요 기능으로 정확히 인지했습니다. 그런데 같은 표의 `sitemap.ts` 행은 "국가 순회 → 팀 순회"만 언급할 뿐, 새로 인정한 fixtures 라우트를 sitemap에 포함한다는 언급이 없습니다.

## 기각된 우려사항 (4건 — 검토 결과 문서가 이미 다뤘거나 근거 부족)

이 부분이 중요합니다: **"1인 프로젝트에 과도한 인프라 아니냐"는 의심(scope-calibration 관점)은 제기된 2건 모두 재확인 단계에서 기각됐습니다.**

- "Phase 0가 무산출 인프라 6개 PR뿐" → 문서가 8장에서 스스로 "산출물은 빈 스켈레톤"이라 인정하고, 7장에서 각 안전장치를 회고의 구체적 사고 사례(4-1 CI, 4-2 브랜치 보호 등)와 하나씩 연결해뒀습니다. 트집이 아니라 근거 있는 선택이었습니다.
- "API-Football 구독 확인이 Phase 1 직전으로 밀려 있다" → 8-0과 10장의 화법이 문자 그대로는 살짝 엇갈리지만(착수를 막는다 vs Phase 1 전), 8-0 자체가 이미 "S0이 안 되면 프로젝트가 성립하지 않는다"고 최우선으로 못박고 있어 실질적 누락은 아니라고 판단됐습니다.
- "라운드 종료 감지가 연기 경기를 못 다룬다" → 4-3에 "N분 무이벤트 후 1회"라는 대안이 이미 명시돼 있어, 이 경로로는 연기 경기 문제가 발생하지 않습니다.
- "다중 리그 확장 시 화면 재작업 필요" → 인용한 사실관계는 맞지만, 문서가 이미 "EPL 단독은 검증 단계"라고 못박고 재작업을 전제하고 있어 새로운 지적이라 보기 어렵다고 판단됐습니다.

## 종합

**scope-calibration(과잉 엔지니어링 의심)은 기각됐다는 게 이 리뷰의 가장 중요한 결론입니다** — 문서가 인프라 투자를 프리핸드로 정당화한 게 아니라 회고와 명시적으로 연결해뒀기 때문입니다. 반면 **진짜 공백은 "동시성"과 "빌드 트리거의 상태 관리"** 두 곳에 몰려 있습니다. 둘 다 스키마·라우트 설계가 아니라 실제 구현 시점에 조용히 데이터가 틀어지거나 사이트가 멈출 수 있는 지점이라, Phase 1 코드를 쓰기 전에 `V2_DESIGN.md`에 한 문단씩 추가해두는 걸 권합니다.
