### 2-2. 컵 6개 — 두 겹의 컷오프 (2026-09-04 실측 확정)

라운드 이름으로 자르지 않는다. 대회마다 체계가 다르고(`5th Round` · `4th Round` ·
`1/8-finals` · `Round of 16`) 손으로 매핑표를 관리해야 한다.
**경기 목록에서 계산되는 두 기준**을 쓴다. 추가 콜이 없다.

```
경기 목록 수집 = 1부 팀이 처음 등장하는 라운드부터
상세 수집      = (1부 팀 참가) OR (16강 이상)
```

**1부 팀 집합**은 `/teams?league={국내리그}&season={시즌}`이다. L0에서 어차피 받는다.

| 컵 | 국내 리그 |
|---|---|
| FA Cup 45 · League Cup 48 | Premier League 39 |
| Copa del Rey 143 | LaLiga 140 |
| DFB Pokal 81 | Bundesliga 78 |
| Coppa Italia 137 | Serie A 135 |
| Coupe de France 66 | Ligue 1 61 |

**16강 판정은 라운드 참가 팀 수로 하되, 마지막 라운드부터 역순으로 16팀 이하가
연속되는 구간만 인정한다.** 팀 수만 보면 예선이 16강으로 잡힌다 —
League Cup `Preliminary Round`는 4팀, Coppa Italia `Preliminary Round`는 8팀이다.
참가 팀이 원래 적은 것이지 토너먼트가 좁혀진 게 아니다.
실측에서 Coppa Italia 예선(Virtus Entella 4-0 Ternana)은 통계가 0이었다 — 헛콜이었다.

잃는 것은 예선 경로다. "6부 팀이 4라운드를 거쳐 올라왔다"를 보여주지 못한다.

결손 플래그를 **대회나 라운드가 아니라 경기 단위**로 두어야 하는 이유다 (4-2 ①).

### 2-3. 대진표 — 골격을 만들고 슬롯을 채운다

목록을 잘라도 대진표는 끊기지 않는다. **골격은 계산으로 만들고 확정된 경기가 슬롯을 채운다.**

컷오프 라운드 이후는 순수 녹아웃이라 구조가 정해져 있다 —
16팀 → 8 → 4 → 2 → 1. 경기가 없어도 슬롯은 그릴 수 있다.

현재 시즌의 골격은 **직전 시즌의 라운드 구조를 템플릿으로** 쓴다. 같은 대회는 매년 구조가
거의 같고, 5개년을 백필하므로 템플릿이 이미 있다. 과거 시즌은 전부 확정이라 문제가 없다.

슬롯 상태는 셋이다.

| 상태 | 언제 | 표시 |
|---|---|---|
| `CONFIRMED` | 경기가 있고 양 팀 확정 | 정상 표기 |
| `PENDING_WINNER` | 라운드는 추첨됐으나 상대가 이전 라운드 결과 대기 | "Round of 32 승자" |
| `UNDRAWN` | 라운드 자체가 아직 추첨 전 | "추첨 예정" / 공백 |

컷오프 이전에서 올라온 팀은 출처를 모르므로 "예선 통과"로만 표기한다.
구체적 표기 문구와 레이아웃은 화면 문서에서 정한다.

### 2-4. 컵의 구조적 차이

- **순위표가 없다.** 전 컵 공통 `standings: false`. L5 #31(순위 재계산)을 컵에는 돌리지 않는다.
- **라운드 문자열 체계가 다르다.** 리그는 `Regular Season - 12`, 컵은
  `Extra Preliminary Round` · `1/128-finals` · `Semi-finals` · `Final`.

- **녹아웃 대진**이 필요하다. `knockout_ties` + `win_reason`(AGGREGATE / EXTRA_TIME / PENALTIES / WALKOVER).
  UCL 전용이던 것이 이제 7개 대회에 적용된다.

## 4. 요청 최소화 규칙

### 4-1. 이미 적용된 것

| 규칙 | 효과 |
|---|---|
| 랭킹은 전용 엔드포인트 | `/players` 23페이지 전수(~400콜) → 대회당 3콜. **95% 절감** |
| `live=all` 대신 리그 지정 | 콜 수는 같고 페이로드가 준다. 전 세계 리그를 파싱하지 않는다 |
| `/fixtures/rounds` 사용 | 라운드 문자열 파싱 제거 |
| `/fixtures/headtohead` 사용 | H2H 자체 계산 불필요 |
| `/teams/statistics` 사용 | 팀 상세를 자체 집계 없이 채운다 |

### 4-2. 새로 정하는 것

**① 결손을 기록한다 — 재수집 방지 ★**

라운드마다 데이터 유무가 다르다. "이 경기는 통계 없음"을 저장하지 않으면 **매 보정 주기마다
같은 경기에 4콜씩 다시 던진다.** 경기 row에 결손 플래그를 두고, 한 번 확인한 결손은 다시 묻지 않는다.

```
data_flags: has_events · has_lineups · has_team_stats · has_player_stats
checked_at: 마지막 확인 시각
```

단, 결손이 영구적이라고 단정하지 않는다. **종료 후 24시간 이내 경기는 재시도한다** —
데이터가 늦게 채워지는 경우가 있다. 그 이후는 묻지 않는다.

**② 라운드 컷오프** (2-2). 컵 하위 라운드에 상세 4콜을 던지지 않는다.

**③ 변화 감지 후에만 이벤트를 받는다.** 라이브 폴링 응답의 스코어·경과 시간이
직전과 같으면 `/fixtures/events`를 부르지 않는다.

**④ `/transfers`는 지연 수집한다.** 선수당 1콜이다. 6대회 스쿼드 전량이면 **약 4,900콜**
(09-07 실측 4,863선수).
선수 상세 화면 진입 시 수집하고 캐시한다. 배치로 미리 받지 않는다.

**⑤ 커버리지 플래그를 수집 조건으로 쓰지 않는다.** 시즌 초에는 전부 `false`였다가 켜진다
(`DATA_RULES.md` 6장). 플래그가 아니라 실제 응답으로 판단한다.

**⑥ 과거 시즌은 다시 받지 않는다.** 종료된 시즌은 L6 보정 대상에서 제외한다.
현재 시즌만 보정한다.

## 5. 백필 실행 계획

### 5-1. Worker다 — Scheduler가 아니다

`V2_DESIGN.md` 5-3의 판별 기준을 그대로 적용한다.

| 기준 | 백필 |
|---|---|
| 한 번에 쓰는 콜 | 45,000 |
| 중간에 죽으면 | **이어서 해야 한다** |
| 실패의 결과 | 데이터가 덜 찬다 (사이트는 돈다) |

→ 재시작 지점을 기억해야 한다. **다만 그것을 BullMQ 가 아니라 `backfill_jobs` 가 한다 (2026-09-07 확정).**
"Worker" 는 실행 방식이 아니라 성격이다 — 트리거는 운영 잡과 같은 `@nestjs/schedule` 이어도 된다.
다른 점은 하나, **자기 진행 위치를 DB 에 남기고 거기서 이어간다**는 것이다.
아래 5-2 의 `cursor_fixture_id` 가 DB 체크포인트이고, 워커는 한 Nest 프로세스 안에서
`@nestjs/schedule` 로 도는 단일 루프다. 1인이 한 번 돌리는 순차 작업에 Redis 인스턴스를
붙이면 장애 지점과 비용만 는다. `V2_DESIGN` 5-3 의 판별("재시작 지점이 필요하면 승격")은
**"체크포인트가 DB 에 있으면 승격이 필요 없다"** 로 읽는다. 다중 인스턴스가 필요해지면 그때 pg-boss → BullMQ 순으로 본다.

워커가 지켜야 할 것 하나 — **일일 상한.** `/status` 로 오늘 쓴 콜을 읽어 5,700 을 넘으면 멈추고
자정 뒤 이어간다. 없으면 첫날 오후에 한도를 다 써서 순위 갱신이 그날 못 돈다 (3-5).

### 5-2. 작업 단위와 재시작 지점

작업 단위는 **(대회, 시즌, 경기)** 하나다. 시즌 단위나 대회 단위로 잡으면
중간 실패 시 되돌아가는 양이 너무 크다.

```
backfill_jobs(
  competition_id, season_id,
  phase,            -- L0 | FIXTURES | DETAILS | RANKINGS | DONE
  cursor_fixture_id,
  total, done, failed,
  started_at, updated_at
)
```

멱등성은 `UNIQUE(match_id, player_id)` 등 기존 제약으로 보장된다.
**같은 경기를 두 번 처리해도 값이 두 배가 되지 않는다** (`V2_DESIGN` 5-7).

### 5-3. 순서 — 최신부터 역순

```
1. L0  기준 데이터 (12대회 × 5시즌)          ~120콜
2.     일정 · 라운드                          ~120콜
3.     2026 시즌 경기 상세                    ~8,700콜
4.     2025 → 2024 → 2023 → 2022 역순         각 ~8,700콜
5.     랭킹 · 팀 시즌 통계 · 선수 시즌 통계    ~1,700콜
```

**최신 시즌부터 채운다.** 오래된 것부터 채우면 9일 내내 아무것도 못 보여준다.

**둘로 쪼개 돌린다 (2026-09-07).** 위 표의 1·2·5 번 — L0 · 일정 · 랭킹 · 시즌 통계 — 는 합쳐야
~2,000콜이라 **하루면 끝난다(백필-1).** 이걸 먼저 받으면 시즌 선택기와 통계 화면이 그날 산다.
3·4 번 경기 상세(백필-2)는 **현재 시즌만 먼저(8,700콜 · 1.5일) 돌려 화면으로 확인한 뒤**
나머지 4시즌을 서버에서 무인으로 돌린다. 쓰기 형태가 틀린 채 5시즌을 돌리면 8일을 두 번 쓴다.
`NEXT_STEPS.md` 8-b · 8-c.

백필-2 가 끝나면 워커의 대상 조건(`detail_eligible AND detail_checked_at IS NULL AND FT`)에는
"어제 끝난 경기" 만 남는다. **코드가 아니라 대상이 바뀐다** — L4 없이도 사이트는 하루 지연으로 완전하다.

### 5-4. 진행 중 사이트 상태

시즌 선택기에 **아직 채워지지 않은 시즌을 노출하지 않는다.** 빈 화면 대신 선택지 자체를 감춘다.
`backfill_jobs.phase = DONE`인 (대회, 시즌)만 선택 가능하다.

부분적으로 찬 시즌은 오해를 만든다 — 순위표가 12라운드까지만 있으면 사용자는 그게 최신인 줄 안다.

### 5-5. 백필 전에 백업을 건다

45,000콜 · 8일치 작업이다. 날아가면 다시 9일이다. Supabase 무료는 백업도 PITR 도 없다.

**2026-09-07 구현됨** — `backend/scripts/`:

```bash
npm run backup          # pg_dump custom 포맷, 홈/PitchLogBackups (로컬 보관)
npm run backup:verify   # 일회용 postgres 컨테이너에 복원해 운영 DB 와 행 수 대조
```

복원 리허설이 통과해야 백필을 시작한다 — 받아본 적 없는 백업은 백업이 아니다.
09-07 리허설: 테이블 31개 · 행 10,062개 전부 일치.
**남은 것은 자동화와 사본 이중화다** (PC 디스크가 죽으면 백업도 같이 죽는다).
자세한 것은 `NEXT_STEPS.md` 4장.

## 6. 실시간 전략

> **시점: 백필-2 가 끝난 뒤 (2026-09-07 확정).** 이유는 3-2 — 폴링과 백필을 같이 돌리면 8일이
> 19~45일이 된다. 그리고 FT 뒤에 부를 L5 확정 코드는 백필-2 가 이미 만들어 검증했다.
> L4 가 하는 일은 그 코드를 하루 지연 대신 10초 지연으로 부르는 것이다.

### 6-1. 폴링 윈도우 — 열고 닫는 근거

10초 폴링을 24시간 돌리면 **하루 8,640콜로 한도를 그것만으로 넘긴다.**
윈도우 개폐가 선택이 아니라 필수다.

```
윈도우 열기  = 오늘 첫 킥오프 - 5분
윈도우 닫기  = 마지막 경기 FT 확정 + 10분
오늘 경기 없음 → 폴링을 아예 돌리지 않는다
```

근거 데이터는 `BACKEND_FEATURES` L2 #17(오늘의 경기 목록)이다. KST 기준으로 산출한다.

### 6-2. 주기 — 10초로 시작, 15초로 강등

| 조건 | 주기 |
|---|---|
| 기본 | 10초 |
| 당일 누적 콜이 6,000 초과 | 15초 |
| 백필 진행 중 | 15초 |
| 진행 중 경기 1경기 이하 | 15초 |

브라우저에는 WebSocket으로 밀기 때문에 **외부 폴링 주기와 사용자 체감은 분리된다.**
15초로 내려도 사용자에게는 즉시 반영된다.

### 6-3. 컵이 윈도우에 주는 영향

컵은 **미드위크에 몰린다.** 리그만 있을 때는 화요일·수요일이 UCL뿐이었는데,
카라바오컵·DFB포칼·코파델레이가 들어오면 미드위크 윈도우가 상시화된다.

- 윈도우 **일수**가 늘어난다 (주 2~3일 → 주 4~5일)
- 윈도우 **길이**는 크게 안 늘어난다 (컵은 동시 킥오프가 적다)
- → 주간 콜 총량은 늘지만 일일 최대치는 비슷하다. **백필 가용일이 줄어드는 것이 실제 영향이다.**

### 6-4. 컵 하위 라운드의 실시간 처리

컷오프 이전 라운드는 이벤트가 없다. 라이브 폴링 응답에 **스코어는 오지만 골 이벤트는 안 온다.**
경기 상세에서 "누가 넣었는지"를 못 보여준다.

→ 컷오프 이전 경기는 **경기 목록에만 노출**하고 상세 페이지를 열지 않거나,
열되 "이 경기는 상세 기록이 제공되지 않습니다"를 명시한다. 화면 문서에서 정한다.

### 6-5. 오버랩 방지

처리 지연이 다음 주기와 겹치면 안 된다. 동시 진행 경기가 많을수록 페이로드가 커지고
파싱·upsert 시간이 늘어난다. 컵 미드위크에 리그와 겹치면 최악이 된다.

- 실행 중 플래그로 중복 진입을 막는다 (단일 인스턴스). 다중 인스턴스 전에는 Redis 락 불필요
- **한 주기 처리 시간을 계측해 기록한다.** 주기의 70%를 넘으면 경고
- Phase 2에서 실제 라운드 1회를 무중단 관측하며 실측한다

### 6-6. 확정 처리는 그대로

경기 중 값은 임시, `FT` 이후가 공식이다 (`V2_DESIGN` 5-7). 컵도 동일하되
**녹아웃은 tie 단위 확정이 추가된다** — 2차전 FT 후 합산·승자·`win_reason` 판정.

## 7. 보관 정책

Supabase 무료 500MB 안에서 5시즌을 유지한다. 추정 296MB(59%).

| 테이블 | 추정 | 정책 |
|---|---|---|
| `player_match_stats` | 36만 행 · 90MB | 5시즌 전량 보관. **전체의 30%로 가장 크다** |
| `lineup_entries` | 48만 행 · 38MB | 5시즌 전량 |
| `fixture_events` | 18만 행 · 22MB | 5시즌 전량 |
| 나머지 | ~35MB | — |

**한계선을 넘을 때의 순서** (지금 정해두고, 넘기 전에는 실행하지 않는다):

1. 벤치 명단(`lineup_entries` 중 미출전)을 과거 시즌에서 제거 — 약 15MB
2. 가장 오래된 시즌의 경기별 선수 통계를 삭제하고 시즌 누적만 유지 — 약 18MB/시즌
3. 그래도 부족하면 Pro 전환

2번은 `V2_DESIGN` 5-7의 "경기별 기록을 원본으로 두고 누적은 집계" 원칙과 충돌한다.
집계를 다시 계산할 수 없게 되므로 **마지막 수단이다.**
